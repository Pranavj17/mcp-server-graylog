# mcp-server-graylog · v2.1.x → v2.2.x Release Journey

**Date:** 2026-05-13
**Releases shipped:** v2.1.0 → v2.1.1 → v2.2.0 → v2.2.1
**Companion deploys:** portfolio worker v2.2.0 → v2.2.1 → v2.3.0 → v2.3.1

This is the design journey for the four releases shipped on 2026-05-13. The `CHANGELOG.md` entries cover *what* changed; this document covers *why* — the live-data discoveries, the false starts, and the feedback loops that produced each version. Written so a future maintainer can understand the reasoning and so a future contributor can follow the same pattern.

---

## The starting point · v2.0.1

Before today the package had six tools — `search_logs_absolute`, `search_logs_relative`, `trace_request`, `get_surrounding_logs`, `list_streams`, `get_system_info` — and one major gap. To investigate a real incident the LLM had to orchestrate three or more tool calls itself: fetch the trace, then surrounding logs, then a baseline count. Three rounds of model reasoning, three prompts, three opportunities for context loss between calls.

## The ask

"Make the package smarter and use the same on portfolio."

Three architectural patterns were on the table:

| Pattern | What it means | Verdict |
|---|---|---|
| **1 · Internal fan-out** | One tool, many internal API calls (composite) | Picked. Highest leverage for a single demo moment, lowest LLM-orchestration cost. |
| 2 · Parallel tool calls | LLM emits N tool_calls in one assistant message | Already supported by the worker; needs no schema change. Deferred. |
| 3 · Server-side mini-agent | Conditional follow-up calls inside a tool | Most powerful but least visible. Skipped. |

The composite (Pattern 1) became `analyze_incident`.

## v2.1.0 · `analyze_incident` · the composite fan-out tool

### Real-data validation came first

Before writing a single line of code, the design was prototyped manually against real Scripbox Graylog production data using the existing MCP tools. Walking through what `analyze_incident` would do — `trace_request` → `get_surrounding_logs` → `count_messages` (baseline) — caught three design issues that would have shipped as bugs:

#### 1. `logger_level` is lowercase in practice

Synthetic-data versions of this package use uppercase `ERROR/CRITICAL/FATAL`. Real Scripbox Graylog returns `"error"`, `"warn"`, `"info"` — lowercase. A naive case-sensitive Set lookup would have silently never matched the anchor, defaulting to "first hop" instead of "first error" every time.

**Fix:** `INCIDENT_ERROR_LEVELS = new Set(['error', 'critical', 'fatal'])` with `.toLowerCase()` on comparison.

#### 2. `get_surrounding_logs` by `source` is too noisy

Scripbox runs many pods on a single EC2 instance. A 10-second surrounding-logs query scoped by `source` (the EC2 instance hostname) returned **756 messages** across argus, advisory, milkyway, clientmaster, and telex — useless context.

The fix that came out of the live test: scope by `pod` instead. The same 10-second window returned **33 messages** — exactly the affected container's view of what happened around the error. **This single decision is the most impactful design choice in the whole release.**

#### 3. Real traces have a recognizable request lifecycle

A typical Scripbox trace looks like:

```
hop 1 · info  · "POST /api/v2/user/graph"           ← entry
hop 2 · warn  · "needs user details"                 ← workflow
hop 3 · ERROR · "resolver: nil fund_id in holding"   ← anchor
hop 4 · info  · "Sent 200 in 67ms"  + http_path,    ← exit (cherries!)
                                      http_method,
                                      http_status,
                                      duration
```

The exit log carries everything an incident summary needs: which API was called, the HTTP outcome, the latency. Extracting this into `summary.request` gives the LLM a one-line "what API was called, did it succeed, how long did it take" without it needing to re-parse the trace.

### What shipped

Schema: `analyze_incident({ traceId, from, to, window?, baselineSeconds? })`

Internal fan-out:
1. `trace_request` style query (`trace_id:X`) → full hop chain
2. Find first error hop as the anchor
3. `pod:<anchor.pod>` filter for surrounding logs in ±window seconds
4. `logger_level:error AND service:<anchor.service>` baseline count over the trailing `baselineSeconds` window

Response (abridged):

```jsonc
{
  "trace_id": "...",
  "found": true,
  "steps_executed": 4,
  "summary": {
    "hops": 4,
    "services_involved": ["argus"],
    "errors_in_trace": 1,
    "anchor_service": "argus",
    "anchor_pod": "argus-production-f747f5d4d-x9hpp",
    "first_error": { "timestamp", "service", "pod", "logger_level", "message", "lead_id" },
    "request": { "http_path", "http_method", "http_status", "duration_ms" },
    "baseline_errors_in_service": 18,
    "baseline_window_seconds": 3600
  },
  "trace_hops": [...],
  "surrounding_logs": [...]
}
```

### Verification

End-to-end smoke test against real Scripbox Graylog 5.0.3 — trace `abbb27610a7fd76be8fb5af17edbe00d`. **12/12 contract checks PASS.** Latency: 2.3s for 3 sequential Graylog API calls. The 4-hop argus trace correctly identified the `nil fund_id` error anchor, extracted the `POST /api/v2/user/graph 200 67ms` HTTP context, and reported a 16/h baseline for the argus service (later confirmed as chronic; baseline grew to 18/h within an hour of the test).

## v2.1.1 · the `api_calls` field · a forensic-driven patch

### The demo that exposed a misnomer

After publishing v2.1.0 we ran a live demo: pulled the freshly-published package via `npx`, called `analyze_incident`, and looked at the response. The field `steps_executed: 4` was being verbally described as "3 API calls." A sharp question — *"how would I know it spun 3 API calls?"* — turned out to have no clean answer in the response.

So we put a local HTTP proxy between the MCP server and Graylog, set `BASE_URL=http://localhost:9999`, and ran `analyze_incident` again. The proxy captured exactly **three** outbound requests:

```
[proxy] #1 GET /api/search/universal/absolute   query=trace_id:170e2e89...
[proxy] #2 GET /api/search/universal/absolute   query=pod:telex-production-...
[proxy] #3 GET /api/search/universal/absolute   query=logger_level:error AND service:telex
```

`steps_executed: 4` was counting the *algorithm's logical steps* (one of which is in-memory anchor selection that hits no network), not API calls. The field name was easy to misread by exactly one — confusing in a way that mattered.

### The fix

Backwards-compatible additive change:

```diff
  "steps_executed": 4,   // algorithm steps · kept for backwards compat
+ "api_calls": 3,        // actual outbound HTTP requests
```

On the `found: false` branch, both become 1 (only the trace lookup runs before bailing). Old consumers keep working; new consumers get unambiguous count. The proxy-based verification technique itself was useful enough to remember — included in this doc as a reusable forensic pattern.

## v2.2.0 · `aggregate_logs` · filling the biggest functional gap

### The missing primitive

"How many errors in the last hour grouped by service?" is one of the most-asked questions in any log-investigation session. Before v2.2.0 the package couldn't answer it directly. The LLM's only option was: `search_logs_relative({query: "logger_level:error", rangeSeconds: 3600, limit: 500})` followed by client-side parsing and counting. Expensive, brittle, frequently hit the 500-result cap on noisy services.

### Why client-side aggregation, not native

The first attempt was the obvious one — call Graylog's native terms-aggregation endpoint. A live probe ruled it out:

```bash
curl https://graylog.scripbox.net/api/search/universal/relative/terms?...
{"type":"ApiError","message":"HTTP 404 Not Found"}
```

Graylog 5.x dropped `/terms`, `/stats`, and `/histogram` from the legacy search API. The replacement is the Views API — a multi-step async dance: POST a search definition, get a search ID, POLL for results. Awkward inside a single MCP tool call.

Plan B that worked: issue ONE regular search with `fields=<group_by_field>` projected. Graylog returns only that field per message (massive bandwidth saver), and we aggregate client-side. Tested with `fields=service` and confirmed Graylog returns `{_id, service, timestamp}` per message instead of the full ~30-field record.

### Implementation contract

```
aggregate_logs({ query, field, from|to|rangeSeconds, size?, fetchLimit?, streamId? })
  ↓ ONE Graylog search with fields=<group_field> projected
  ↓ Iterate, group, count
  ↓ Sort desc, slice top N, sum the rest into `other`, count `missing` separately
returns: { top, other, missing, truncated, unique_groups, total_matched, api_calls: 1 }
```

Caps at `fetchLimit` (default 5000, max 10000). When `total_matched > fetchLimit`, sets `truncated: true` so the caller knows to narrow the window.

### Live findings from validation

Five contract checks against Scripbox Graylog 5.0.3 — all PASS, with a couple of real-world signals worth recording:

| Test | Findings |
|---|---|
| Errors in last 30min grouped by service | 30 total · top: milkyway:8, argus:4, telex:4, advisory:3, auth:1 · **`missing: 10`** (10 errors had no service tag → log-hygiene issue worth surfacing to whoever owns those streams) |
| All logs in 5min grouped by logger_level | 44,091 matched, 1000 fetched, **`truncated: true`** correctly flagged |
| Validation: missing time params | Rejected: `"Provide EITHER rangeSeconds OR both from+to"` |
| Validation: `field: "service; DROP TABLE"` | Rejected by field-name regex |
| 1h argus errors grouped by pod | `argus-production-argus-bg-6499897946-rnz7v` carries 9 of 21 → background workers dominating, single hottest pod identified in one tool call |

The `missing` count surfacing log hygiene problems was an unexpected bonus — anyone running this against their own Graylog can immediately see "we have N logs missing critical metadata."

## v2.2.1 · structured observability · closing the silent-error gap

### What the previous error path looked like

Two distinct error-handling tracks existed, and they treated logging completely differently:

- **HTTP errors from Graylog** got a structured `console.error` on stderr via `graylogRequest`'s catch block — visible, grep-able.
- **Everything else** — validation errors, parse errors, JS bugs in handlers — was silently caught by the top-level catch and returned only to the MCP client as `isError: true`. Zero server-side trace.

If a user reported "the tool failed earlier today" there was no way to grep the server logs for the relevant request. The HTTP error log line didn't even carry the tool name or args, so even when stderr *did* have something useful it couldn't be correlated back to the failing investigation.

### The fix

Three stderr lines around every tool dispatch, plus an `redactArgs()` helper:

```
[graylog-mcp] tool_call: <name> <redacted-args>
[graylog-mcp] tool_done: <name> · <ms>ms
[graylog-mcp] tool_error: <name> · <ms>ms { message, args }
```

`redactArgs()` masks keys matching `/token|password|secret|auth|cred|apikey/i` and truncates string values >200 chars. Current tools accept no credentials but the redactor future-proofs against handlers that someday do.

Implementation extracts the dispatch switch into a `dispatchTool(name, args)` helper so the logging wrapper around it stays compact.

### Verified

8/8 contract checks pass in an end-to-end smoke test that spawned the server, piped its stderr through a buffered reader, issued a happy `aggregate_logs` call + a deliberately failing one (missing `field`), and inspected the captured output. Critically the negative check — `API_TOKEN` must NEVER appear on stderr — passed: redaction works.

## What this all leaves

| Metric | Before today | After today |
|---|---|---|
| Tools | 6 | **8** (added `analyze_incident`, `aggregate_logs`) |
| API calls per investigation | ~3-4 LLM rounds | **1** (`analyze_incident` for trace work) |
| Aggregation queries | Client-side parse loop | **`aggregate_logs` native tool** |
| Server-side error visibility | HTTP errors only | **All errors logged with args + timing** |
| Response transparency | `steps_executed: 4` (misleading) | **`api_calls: N` explicit** |

The package surface is now substantively larger and substantively more honest. Visitors of the portfolio demo see the same tool list against synthetic data; users of the npm package see it against their real Graylog.

## Patterns worth reusing

A few practices proved themselves repeatedly during the day. Worth naming so we can deploy them deliberately next time:

### 1. Validate against real data BEFORE writing code

Every release this day started by manually walking the data flow through the existing MCP tools against real Scripbox Graylog. The discoveries that shaped the design (`logger_level` lowercase, pod-scoped surrounding, HTTP-exit-log cherries, terms-endpoint 404) would have been bugs or wasted iterations if found only after code was written.

### 2. Proxy verification for tool audits

When the question is *"is this tool actually doing what it claims?"* — put an HTTP proxy in front of the backend. Reveals API calls, latencies, query parameters, and response sizes that would otherwise require trusting the tool's self-reported metrics. Caught the `steps_executed` misnomer in v2.1.0.

### 3. Schema mirroring with synthetic backing

The portfolio worker doesn't talk to real Graylog; it serves synthetic data over the same MCP surface. Keeping the response shape interchangeable with the real package (same field names, same types, even when synthetic values are always `null`) means demo visitors see exactly what real users see. The cost is honesty about which fields the synthetic data populates — documented in code comments.

### 4. Same-day patch loops on small fixes

The day produced **4 releases** in part because the friction was low: `npm publish` was a one-liner after `~/.npmrc` got the bypass-2FA token, and the smoke-test pattern was reused across every release. Small releases at high cadence beat one big release once a quarter — each one had a smoke-test contract that proves the change holds.

### 5. Co-shipped portfolio mirror

Every package release was followed within minutes by a portfolio worker deploy mirroring the same surface. The portfolio became the *public live demo* of the npm package — anyone visiting `pranavjagadish.com/mcp` is running the same tool surface as anyone with the package installed. The two stay synchronized because the portfolio version explicitly tracks which package version it mirrors in code comments + status-endpoint version.
